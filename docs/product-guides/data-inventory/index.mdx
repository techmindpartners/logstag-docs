# Data Inventory

Data Inventory is in Beta. It classifies the schema metadata of monitored databases (table, column, and field identifiers) to flag where sensitive-data categories are likely to live.

Metric definitions for the Data Inventory list page and the table detail view live in the
[Overview reference](./overview.mdx) and the [Detail reference](./detail.mdx).

## Purpose

Data Inventory helps operators and security-minded teams answer questions such as:

1. Which tables are likely to contain PII, payment data, or credentials, based on their schema?
2. Which sensitive-looking tables are unencrypted?
3. How exposed is a sensitive table, based on who can access it?
4. Which databases and schemas need closer review before an audit or a data-handling decision?

Data Inventory presents its results as a KPI strip summarizing sensitive-data exposure across monitored databases, followed by a findings table listing each classified table with its data-type categories, encryption status, access level, and a computed risk level. The table can be searched and filtered by engine, schema, encryption status, and risk level.

## How Classification Works

Classification runs automatically, without a manual tagging step. It is model-assisted: automated analysis reviews collected schema identifiers and assigns one or more sensitive-data categories with a confidence score, based on naming patterns rather than the underlying data.

Classification work is triggered by:

- A detected schema change on a supported database.
- A daily check of each database.
- A change to the organization's rules that brings excluded tables back.

Each run sends only tables that are new or changed since their last classification; every other table keeps its stored result. Runs are saved in parts, so a run that stops partway (for example on the model's quota) keeps what it finished, and the rest goes in a later run. A table whose answer comes back empty keeps its previous result until a re-check.

## Rules

Admins and DBAs can adjust what Data Inventory reports, per organization, under **Data Inventory → Rules**. Rules are applied when pages load, after the model's answer: the answer itself is kept, so a rule shows at once and can always be undone.

- **Column names**: columns whose name matches a pattern (`*` for any text, `?` for one character, upper and lower case the same) lose the chosen categories, or all of them. The **IP addresses are not PII** switch adds three editable rules for IP address, host name and MAC address columns.
- **Categories**: a category can be turned off for the whole organization.
- **Exclusions**: a database, schema or table is left out of Data Inventory and is not sent to the model. Its earlier results are kept, so removing the exclusion brings them back at once.
- **Column overrides**: on a table's detail page, a column the model flagged can be set by hand, including "not sensitive".

When rules disagree, the order is fixed: exclusion, then category off, then column override, then column name rule. A preview shows how many columns and tables a rule changes before it is saved. The detail page shows which rule changed each column, lists the flagged columns a rule hid, and says when the whole table is excluded. The PDF report lists the active rules.

## Categories

Logstag classifies columns and fields into these categories:

| Category | Examples of what it covers |
| --- | --- |
| PII | Names, emails, phone numbers, national ID numbers, dates of birth. |
| Financial | Bank account details, salaries, invoices, credit scores. |
| Credentials | Passwords, tokens, API keys, session identifiers. |
| Payment | Card and other payment-instrument data. |
| Health | Diagnoses, prescriptions, lab results, medical record numbers. |
| Location | Street addresses, postal codes, GPS coordinates. |
| Legal | Contracts, consent records, litigation data. |
| HR | Employment records not covered by Health. |

A column or field can be classified into more than one category. Generic container columns, such as a JSON payload or blob field, are not classified based on what they might contain.

## Engine Scope

Classification currently runs for PostgreSQL, Microsoft SQL Server, and Oracle. On Oracle, each owner is treated as a schema, and only tables are classified (not views or materialized views). Other supported engines can appear as monitored targets, but Data Inventory does not classify them today.

Encryption status is currently reported for Microsoft SQL Server, based on transparent data encryption. Tables on other engines show an unknown encryption status, with no claim either way.

## Data Boundaries

Data Inventory classifies schema metadata only: schema names, table names, column names, and field names. It does not read row contents, document contents, or key values from monitored databases. Classification never touches application data, only the identifiers that describe where that data would live.

Because classification works from names only, treat a finding as an indicator to review; it does not confirm compliance. Column and field names that don't clearly describe their contents can be classified incorrectly or missed. Access to Data Inventory should be limited to users who are allowed to review sensitive-data exposure across the organization's databases.

## Beta

Data Inventory is a Beta product surface. Scope is still expanding:

- Classification covers PostgreSQL, Microsoft SQL Server, and Oracle only; other monitored engines are not classified.
- Encryption status is tracked for Microsoft SQL Server only; other engines report as unknown.
- Access level is computed per schema, so every table in a schema shares the same value. Oracle admins who reach every table (DBA, SELECT ANY TABLE) aren't counted yet.
- Runs can lag a schema change by up to a day, and coverage can look incomplete for a database that was only just added.

A point-in-time PDF export of this data, including a risk register and encryption coverage, is available from the [Data Inventory report](../reports.mdx#data-inventory).
